- POST のボディと X-API-Key を確認。メディア配信先へのリクエストにはキーが付いていないことも確認。
- 音声の再生時間が進み、A → B → C の3曲が自動で連続再生。
- 次の曲への移動、停止、現在の曲の表示を確認。
- MP4 の再生時間が進み、動画終了後に次の曲へ自動移行。

## ブラウザー確認の再現

クラウドには Chromium、Python Playwright、FFmpeg が用意されています。以下をリポジトリのルートで実行し、HTTP サーバーは別のターミナルで起動してください。

~~~bash
bash scripts/flutterw build web --no-pub --no-web-resources-cdn
python3 -m http.server 8080 --bind 127.0.0.1 --directory build/web
~~~

~~~bash
ffmpeg -hide_banner -loglevel error -f lavfi -i sine=frequency=440:duration=12 -c:a aac -b:a 96k /tmp/mix-smoke.m4a
ffmpeg -hide_banner -loglevel error -f lavfi -i color=c=0x132234:s=320x180:d=12 -f lavfi -i sine=frequency=440:duration=12 -c:v libx264 -pix_fmt yuv420p -c:a aac -shortest -movflags +faststart /tmp/mix-smoke.mp4
python3 scripts/smoke_web.py
~~~

生成済みのテスト音源を作り直す場合は FFmpeg に -y を追加してください。スモークテストの API キーは公開のテスト用文字列です。実際の接続先や鍵をテストコードへ記載しないでください。

## 2026-10-29 再生開始までの待ち時間

一覧を取得したら先頭曲のURLと音声を読み込み、タップ時は同じ準備とプレーヤーを使います。自動再生は行いません。次の2曲のURL取得は先頭曲の準備後に進め、最初の再生開始ではその完了を待ちません。

一覧タップと前後移動は、有効なURL・ヘッダーを持つキューを再利用します。API結果の保持はクライアントごとに最大16曲・5分で、URLの `expire` が分かる場合は30秒前から再利用しません。同じ曲への処理中のリクエストは共有し、再利用した音声の失敗時は1回だけ新しいURLを取得します。API設定変更でキャッシュも破棄します。サーバーのAPI契約は変更していません。

Chromiumで、テスト用APIの応答に1秒、メディア応答に0.4秒の待ち時間を入れ、各操作を5回測定しました。指標は画面のpointerdownからHTML audioのplayingイベントまでです。

| 条件 | 変更前の中央値 | 変更後の中央値 |
| --- | ---: | ---: |
| 最初の曲（タップ前に読み込み完了） | 1.584秒（事前読み込みなし） | 0.155秒 |
| 最初の曲（一覧表示直後にタップ） | 未測定 | 1.439秒 |
| 先読み済みの曲を一覧からタップ | 1.520秒 | 0.541秒 |
| 直前の曲へ戻る | 1.611秒 | 0.554秒 |
| 「次の曲」ボタン | 0.485秒 | 0.544秒 |

変更後は5反復すべてで、準備済みの先頭曲のタップ、一覧タップ、前の曲への移動によるURL再取得が0回でした。一覧表示直後のタップも、既に進行中の先頭曲の問い合わせを共有し、重複取得しませんでした。タップ前に音声が再生されないことも確認しました。

準備済み条件は、URL取得とメディア読み込みをタップ前に済ませた場合の測定です。直後にタップすると残りの準備時間を待ちます。実際のAPIサーバー、Tailscale、iPhoneの通信・デコード速度や物理的な音声出力までの時間は未測定です。
